# 决策记录规范

这里存放一类设计文档。**Agent Note** 记录影响本仓库的决策或提案：代码和文档无法承载的*为什么*以及*放弃了什么*。本文件规定 Agent Note 存放在哪里、何时需要写一份，以及[文件格式](#文件格式)。

## 布局与命名

每份 Agent Note 有两个维度，都编码在其**路径**中：`{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`。

- **生命周期**（顶层文件夹）是 Agent Note 的状态，Agent Note 随状态变化在文件夹之间移动：
  - **`proposed/`**：实施前评审的提案；尚未构建或仅部分构建。规则见[提案记录](proposed/AGENTS.md)。
  - **`implemented/`**：决策已交付。文件记录做了什么决定、否决了什么，并**与实际交付的内容保持同步**：当代码移动文件、重命名包或更改键名/默认值时，Agent Note 在同一个变更中同步更新（仅限事实——路径、名称、结构——而非决策本身）。规则见[已实施记录](implemented/AGENTS.md)。
  - **`rejected/`**：提案经过讨论后被否决。仅当其依据仍能避免一种诱人且影响重大的错误时保留；否则删除。规则见[已否决记录](rejected/AGENTS.md)。
  - **`archived/`**：已实施但不再指导未来工作的记录，冻结保存，不作为当前权威。规则见[冻结归档](archived/AGENTS.md)。
- **类别**（嵌套文件夹）是决策的*种类*——见下方[分类](#分类)。

文件名中的日期是该主题**首次提出**的时间，以已有记录或 Git 历史为准，不是最后修改日期；文件名使用简短的小写英文、数字和连字符。交叉引用使用相对 Markdown 链接（`[主题](../../implemented/architecture/2026-…-….md)`），从不使用纯文字或编号，这样既可机械检查，也能在文件夹间移动时保持有效。

活跃生命周期目录树就是工作清单：浏览生命周期/类别文件夹，或搜索仓库。请勿添加集中式 `INDEX.md`：它重复路径元数据，并让无关记录的变更争用同一个文件。类别目录随首份记录创建；不为空类别建立占位页。

## 分类

每份 Agent Note 属于检查器中封闭集合里的一个路径编码类别；分类检查拒绝其他文件夹。新增类别需要同时更新规范集合与本节。

| 类别 | 覆盖范围 |
|---|---|
| `feature` | 面向用户或 Agent 的新能力。 |
| `bug-fix` | 修正缺陷，或弥补复盘发现的缺口。 |
| `simplification` | 在不增加能力的前提下移除代码、行为或对外范围。 |
| `architecture` | 关于**交付源码**的结构性决策：模块关系、运行时模型与契约。 |
| `process` | 源码**周边**的工具、策略或工作流——文档检查、包管理、发布流程——不涉及运行时行为。 |
| `testing` | 测试基础设施与验证策略。 |

`architecture` 与 `process` 的界线：**architecture** 关乎我们交付的源码；**process** 关乎围绕源码的工具与工作流。（`refactor` 被有意排除：它与 `simplification` 重叠，而后者的判别标准“可观察行为是否改变”已经覆盖了它。）

## 归档与删除

仅描述小型 UI 调整或纯机械变更的 implemented Agent Note 直接删除；一并删除文件并修复或移除入站链接。局部 bug 修复、性能变更、新能力或实质行为决策，不会仅因实现规模小就符合删除条件。

其他已实施记录只有在交付决策完整落地、其依据不太可能再指导未来工作，但仍具有历史决策价值时才归档。如果其中的备选方案、归属边界、否定性保证、持久化或协议语义、安全规则，或者重新引入条件仍有价值，则继续作为活跃记录保留。绝不归档 proposed Agent Note：过时的提案应转为 rejected。仅当 rejected Agent Note 仍能避免一种可能发生的错误时保留；否则删除。

归档路径编码为 `archived/{class}/yyyy-mm-dd-topic-title.md`；其中有意省略 `implemented`，因为只有 implemented Agent Note 可以进入归档。归档变更移动记录，保留 `Status: implemented`，紧接该状态行插入 `Archived: YYYY-MM-DD`，并修复或删除入站链接。归档时只允许这些内容更改。

封存后，归档记录永久冻结。禁止编辑、翻译、重排、更新、移动或删除，也不得将其视为当前行为的权威依据。文档检查跳过归档正文，但活跃文档有意引用历史时，仍可链接到归档 Agent Note，并检查其目标与锚点。

### 判据尺度

判据是语义判断，篇幅只作发现线索。以下给出尺度，不新增规则：

- **保留：** [文档系统决策](implemented/process/2026-11-06-documentation-system.md)（约 1070 个汉字）记录结构选择、被否决的方案与主动放弃的能力，仍约束当前文档工具，因此保持活动。
- **删除：** 一次界面微调或纯机械改名，正文只剩「改了什么」，没有备选方案、归属边界或重新引入条件。
- **归档：** 决策已完整落地，备选方案与代价不再影响后续选择，但历史依据仍有留档价值。
- **否决保留：** 落败方案仍可能被重新提出，误采用的代价明显。**否决删除：** 该方案的前提已从代码与文档中消失。

## 何时需要写一份

只有代码、测试和现有文档未能解释的决策理由具有长期价值时，才在同一变更中新增或更新 Agent Note。对未来重大工作的提案从 `proposed/` 开始；已经做出的决策从 `implemented/` 开始。选择与决策匹配的类别文件夹（见[分类](#分类)）。

更新已经拥有该决策的 Agent Note 即可满足规则；不要创建重复记录。机械性或局部编辑均可豁免，包括局部 UI 展示和交互调整。Agent Note 永远不会被编辑为一个*不同的决策*：用新 Agent Note 取代旧记录，并让两个记录保持互相链接，除非后续依据下方规则完全合并旧记录。编辑 `implemented/` Agent Note 以跟踪其现有决策的所在位置是必需的，而非禁止的；见 [implemented/AGENTS.md](implemented/AGENTS.md)。

被完全取代的 implemented Agent Note 可以合并到当前持有该决策的记录中，并删除原文件。删除前，当前记录必须保存所有独有的决策依据、备选方案、影响、必需的验证和明确指出的覆盖缺口；修复所有入站链接。仅部分被取代的记录不符合此条件：保留两个记录并让它们互相链接，同时更新所有仍然适用的事实。合并不得将旧文件改写成与其相反的决策，也不得让版本历史成为决策依据的唯一副本。

只有当一项功能已从生产代码、配置、schema、持久化或协议格式、迁移和兼容行为中完全消失，当前文档不再将其描述为可用，且没有测试把它作为受支持行为来执行时，新增该功能的 Agent Note 才可合并进后续的移除记录。移除记录必须保留最初动机、为什么该动机已不足以证明保留该功能的合理性、完全移除之外的备选方案、放弃的能力、重新引入的条件，以及证明已彻底移除的验证。过时的实现清单和只验证已删除行为的测试不属于当前验证证据。仅移除一种传输、默认值、实现或展示属于部分取代；仍有任何持久数据或兼容处理也同样如此。

## 文件格式

每份活跃 Agent Note 遵循统一的文件内格式，由 `pnpm docs:check` 强制执行。归档记录保留封存时的格式，并增加上述归档日期行。

### 头部块

每份 Agent Note 的前四行严格为标题、空行、状态行、空行：

```markdown
# 决策记录：标题

Status: implemented

```

`Status:` 的值有三种形式，且必须与文件所在的生命周期文件夹一致——检查器会交叉检查：

```text
Status: proposed
Status: implemented
Status: rejected — 一行拒绝理由
```

状态行不带日期、版本或括号补充说明：文件名记录首次提出日期，Git 记录其余一切；修订说明属于正文内容，写在陈述决策的地方。拒绝理由是唯一带内容的状态，因为读者查阅被否决的 Agent Note 时，结论正是他们要找的。

### 正文骨架

每份 Agent Note 的正文以 `## 问题` 开头：动机，写法上不依赖解决方案即可独立成文。后续内容取决于生命周期；固定章节使用以下规范名称且仅限这些名称，而真正独特的技术章节（模块拓扑、协议约定、schema 等）在必需章节之间可自由组织。

#### `proposed/`

```markdown
## 问题
## 提案
…自定义章节…
## 备选方案
## 验收标准
## 风险
```

`## 提案` 描述拟议的变更，可以合理地使用将来时——计划、迁移步骤和待解决问题在工作尚未完成时属于此处。`## 验收标准` 说明什么可观察状态意味着完成。`## 风险` 涵盖可能出错的事项以及该变更有意放弃的东西。

#### `implemented/`

```markdown
## 问题
## 决定
…自定义章节…
## 备选方案
## 后果
```

`## 决定` 以现在时态描述已交付的现实，整个文件按 [implemented/AGENTS.md](implemented/AGENTS.md) 的要求与之保持同步。`## 后果` 记录权衡的代价**与**收益。提案阶段的标题在此属于规格用语，检查器会拒绝它们：`## 提案`、`## 计划`、`## 迁移计划` 和 `## 验收标准` 不得出现在 implemented Agent Note 中。`## 测试`、`## 暂缓` 或 `## 关联` 章节在陈述现在时态的事实时是允许的。

#### `rejected/`

被否决的 Agent Note 是冻结的提案：保留提案时的所有章节（包括 `## 验收标准` 或 `## 计划`），结论写在 `Status:` 行上。仅头部块、`## 问题` 开头、`## 提案` 章节以及下方的“曾考虑的替代方案”强制要求适用。

### 曾考虑的替代方案——必需

每份 Agent Note 都必须包含 `## 备选方案` 章节：每个真实的替代方案及其落选原因，每个替代方案用一个加粗引导的段落，或对争议较大的替代方案用 `### 为什么不采用 <方案>？` 子节。记录决策时不记录它击败了什么，就是在邀请反复争论——这正是 Agent Note 旨在防止的问题。

替代方案是记录下来的，不是凭空编造的。不得为凑格式编造当时未考虑过的选项；确实没有记录且无法重建时，明确写出这一证据缺口，不写成已经做过比较。

### 在生命周期之间移动

将文件在生命周期文件夹之间移动意味着在同一个变更中更新 `Status:` 行、目录和正文骨架，否则检查器会失败。具体而言，`proposed/` → `implemented/` 将 `## 提案` 改写为现在时态的 `## 决定`，将 `## 验收标准` 和 `## 风险` 折入 `## 后果`（或折入一个现在时态的 `## 测试`/`## 验证` 章节），并用实际交付的内容替换计划。`proposed/` → `rejected/` 仅在 `Status:` 行添加原因并冻结文件。

重新考虑被否决方案时，创建新的 `proposed` 记录，链接原记录并说明条件变化，不删除原拒绝理由。转为 `archived/` 只适用于已实施记录，按[归档与删除](#归档与删除)处理。

每次转换保留首次提出日期和文件名，并修复全部活动入链。不得只改状态行而保留原正文，也不得为让检查通过而删掉仍适用的技术约定。状态本身不证明验证通过：记录中的“已验证”必须对应真实执行过的路径。

### 校验边界

`pnpm docs:check` 按封闭集合检查路径与目录：`.agents/notes/` 下只允许 `proposed`、`implemented`、`rejected`、`archived` 四个生命周期目录；生命周期根只允许 `AGENTS.md`；类别目录只允许六个登记类别，且不再嵌套子目录；拒绝 `INDEX.md` 和散落记录。

格式检查覆盖固定头部、状态与目录一致、`问题` 首节、各状态的必需章节，以及 implemented 记录中的提案章节。归档记录只检查身份元数据、归档日期位置和类别目录，跳过正文结构、围栏和旧出链；活动页指向归档的链接仍检查目标与锚点。

检查器不验证首次提议日期的历史依据、方案是否真正交付、拒绝正文是否原样保留、归档是否被改写，也不判断替代方案是否真实。这些由审阅负责。通过检查不等于记录正确。

起稿时复制上方对应生命周期的骨架代码块；骨架不是已发生的决定或执行证据。
