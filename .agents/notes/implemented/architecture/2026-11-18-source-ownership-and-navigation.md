# 决策记录：源码所有权与导航边界

Status: implemented

> CLI 命令面由[声明驱动的 URL 命令入口](2026-11-18-declaration-driven-url-cli.md)继续收敛；本文保留源码所有权、公开分面与导航组织的决定。

## 问题

CLI 命令、Core 协议和领域 operation 的组织方式不同，部分公开入口同时承担装配和实现；调用方需要跨大文件寻找职责，领域错误、输入校验和资源释放也存在多处解释。仅调整格式或按文件长度拆分，不能改善变更局部性。

## 决定

源码按领域聚合，领域内部区分公开契约、用例与适配器。Core 根入口只负责运行时创建，协议、组件、安全、Workspace、事件和存储通过显式公开子路径消费；包内直接依赖实现文件，不经过公开 barrel。所有消费者迁到所属分面，不保留旧入口转发。

CLI 用静态组件清单装配，命令域、可信 Host、输出和 shell 各有归属；名称解析、领域校验和持久化用例属于 operation 或领域服务。业务包拥有自己的错误到协议映射，operation 交付可序列化结果；原生流和客户端对象留在适配器内。

Security Runtime 保留 Session、Challenge、Grant 的对象身份、撤销和并发消费；授权、凭据及 Root 认证用例通过具名窄接口分离，不暴露协调器内部状态。组件元数据深度冻结，operation 外壳冻结；schema 是外部执行对象，不递归冻结其内部缓存。Dispatcher 的结果分类与执行事件位于捕获闭包内，Grant 恢复也走同一错误边界。

模块 README 维护修改场景到源码和测试的短导航，不复制符号清单、完整目录树或行号。Prettier 统一代码外观，ESLint 守护静态依赖边界，TypeScript 保持跨包 declaration map 与显式类型导入。

## 备选方案

**只拆长文件并格式化**：不能消除公开面混杂、反向领域知识和多入口行为差异。

**横向拆成 contracts、runtime、shared 等独立包**：现有消费关系不需要新增发布边界，会增加导航和版本维护成本；本次只重组既有包内部。

**动态发现组件或生成命令平台**：会扩大运行时与安全模型，不能解决当前显式装配信息重复的问题。

## 验证

Windows x64 上分别执行 `pnpm build`、`pnpm lint`、`pnpm format:check` 与 `pnpm test:all`，174 个行为用例通过；`pnpm e2e` 完成 36 次真实 CLI 调用，未跳过冷却。覆盖领域错误、schema 输出、直接 operation 私钥校验、授权恢复、事件终态、HTTP DTO、临时凭据清理和实际 CLI 输出。原生 Keyring 隔离账户、真实远端生产目标及其他 OS 未在本次重跑，不外推已有平台证据。

## 后果

公开入口重组是破坏性开发期切换，不提供兼容转发，仓库消费者、测试和脚本使用所属分面。代价是需要按领域选择入口；收益是公开面和实现归属可直接定位，不再依赖根 barrel 或跨领域大文件。

外部操作完成后的清理失败与执行结果区分，不能静默成功或诱导自动重试。目录组织、格式与依赖边界成为持续维护的门禁；模块导航链接到事实所有者，不形成第二套 API 清单。
