# 决策记录：本机部署只维护一跳数据迁移

Status: implemented

> 取代 [Core Security 统一权限与凭据平面](2026-11-15-core-security-runtime.md)与[统一资源调用与 operation 授权](2026-11-17-invocation-api.md)中“开发库不维护旧 schema 迁移、按当前结构重建”的数据库兼容部分；其余决定仍以这两篇记录为准。

## 问题

本机部署的 Locus 已承载真实 Workspace、关系、挂载、组件状态与凭据元数据。此前约定开发库不承诺旧 schema 兼容，结构变更按当前 schema 重建；这条约定把每次结构升级都变成一次人工数据重建或丢弃，本机部署已经无法承受。

部署范围只针对本机，不对外承诺所有 Locus 版本都能升级，因此不需要随产品发布长期迁移链，也不能让运行时依赖未入库的迁移文件。

## 决定

Locus 自有、带 `user_version` 的持久数据（当前只有 `core.sqlite`）每次结构变更只维护一份迁移：从紧邻的上一个版本到当前版本。脚本放在仓库的 `temp/migrations/`，例如 `core-v8-to-v9.sql`；`temp/` 已被忽略，脚本不入库、不随构建发布、不进入运行时。

提升 `CORE_SCHEMA_VERSION` 与编写迁移属于同一变更。升级步骤固定为：停止全部写者，复制整个数据目录，在单事务中执行脚本并把 `PRAGMA user_version` 更新到目标版本，`PRAGMA integrity_check` 通过后用新构建启动并抽查数据。升级完成后保留当前版本的一份迁移；新版本落地后可删除更早的脚本。

运行时保持拒绝不匹配版本，不读取 `temp/`、不自动迁移、不覆盖未知数据。只保证落后一个版本的本机数据库直接升级；跨多个版本、降级与历史格式兼容不在承诺内，需要时先恢复到备份，再按 Git 历史逐版本执行，或由用户明确选择重建。OS Keyring、用户凭据文件与外部资源不属于该迁移范围。

## 备选方案

**继续按当前 schema 重建**：否决。本机数据已有保留价值，重建会丢失 Workspace 关系、组件状态与凭据元数据，且要求用户每次升级重新登记。

**在仓库中提交完整迁移链**：否决。只有本机部署，没有对外兼容承诺；长期维护逐版本脚本、升级／降级分支与历史格式测试的成本高于收益。

**运行时读取 `temp/migrations/` 自动迁移**：否决。产品会依赖未入库、未随构建交付的本地文件，启动时产生不可预期的写入，并绕过停写与备份前提；迁移必须是显式的本机操作。

**把脚本放到 `docs/upgrade-guide/`**：否决。该目录面向需要用户执行迁移的对外破坏性变化；本机一跳迁移是仓库维护者的操作工件，不是消费者文档。

## 后果

本机升级不再丢弃数据，代价是迁移脚本不经过 Git 审阅与发布，只能靠备份、单事务与完整性检查兜底；操作者必须严格按相邻版本升级，跳过版本时没有可用迁移。

迁移脚本会随时间删除，历史格式不再有可执行副本，但重建脚本所需的事实仍来自各版本 DDL、Git 历史与 `user_version`。当前数据库版本已与 `CORE_SCHEMA_VERSION` 一致，没有待交付的一跳；下一处结构变更按本记录在同一变更中产生脚本。
