# 决策记录：Gitea Instance、Repository 与 Actions Run 观察

Status: implemented

## 问题

Workspace 已能通过 Filesystem、Git、Remote Machine、Connectivity 与 Session 聚合本地与远端资源，但还不能回答：

- 一个 Workspace 对应哪些真实 Gitea 仓库？
- 本地 Git HEAD 是否已有远端 CI 结果？
- Run 是成功、失败、运行中、取消、未知，还是根本没有落到远端？
- 实例不可达、凭据失效、Actions 未启用或 API 不支持时，如何不把访问失败误写成“没有流水线”？

Gitea 拥有仓库、Workflow、Run、日志、Artifact、Secret 与权限的原生事实。Locus 不应复制 Gitea 数据库、后台同步流水线历史，也不应把 CI 成功当成部署或服务健康。

真实条件：Gitea `1.25.5`，SQLite，Actions 已启用；5 个私有仓库，均有历史 Run。API 支持 `/repos/{owner}/{repo}/actions/runs`、`/actions/runs/{run}`、`head_sha` 过滤和 `/repositories/{id}`。列表响应可以不返回 Run 时间，且实测忽略 `limit`。

## 决定

本轮交付 Gitea v0：只读实例、仓库、Run 与本地 Git 对应关系观察。

### 身份

- `GiteaInstance` 是本 Plugin 的 UUID，不是 Machine，也不要求 SSH。
- `baseUrl` 只用于定位；修改地址不改变 Instance ID。
- Repository 引用为 `locus.gitea.repository` + `${instanceId}:${repositoryId}`。
- 使用 Gitea 数字仓库 ID，而不是 owner/name。仓库改名后通过 `GET /api/v1/repositories/{id}` 解析当前完整名称；删除、迁移或权限变化保留旧引用并报告不可用。
- Workspace 关系仍保存在 Core。Gitea Plugin 不复制成员模型，也不把 Git Remote 相似性当成身份。

### 持久化

`gitea.sqlite` 只保存实例：`id`、`name`、`base_url`、`credential_ref`、时间。仓库、Workflow、Run、日志、Artifact、Secret 与临时访问结果均不持久化。

不保存 Run 历史，不建立后台同步。每次命令重新查询；列表默认 10、最多 100，客户端强制截断。

### 凭据

`credentialRef` 只保存 POSIX 名称，例如 `GITEA_TOKEN`：

1. DSH `credentials` 服务存在时优先 `resolve(name)`，复用其本地存储、启动环境与 `.env` 层。
2. 缺失时回退读取启动环境同名变量。

Token 不进入配置、Workspace、Core、错误、日志或 JSON。请求使用 `Authorization: token …` Header；`redirect: 'manual'`，3xx 报告 `redirect` 而不跟随；超时 10 秒，响应上限 1 MiB，只接受 JSON。

### API 观察与状态

- `inspectRepository` / `inspectReference`：仓库 ID、完整名称、默认分支、私有/归档、`hasActions`、网页 URL。
- `runs`：默认/上限、`branch`、`head_sha` 过滤。
- `run`：单条详情，含状态、结论、提交、分支、工作流路径和时间。
- `verifyInstance`：版本与凭据检查。
- `suggest`：只比较 Remote URL 与已登记实例，不访问 API、不写关系。

Run 保留原始 `status` / `conclusion`，另给出产品 `outcome`：

- `completed + success` → `success`
- `completed + failure/timed_out/startup_failure/action_required` → `failure`
- `completed + cancelled` → `cancelled`
- `running` / `in_progress` → `running`
- `queued/requested/waiting/pending` → `pending`
- `completed + skipped/neutral/stale` → `other`
- 其余 → `unknown`

访问失败与空结果分开：

- `empty`：请求成功但没有 Run。
- `actions-disabled`：仓库 `hasActions=false`，不请求 Run。
- `unsupported`：仓库可访问但 Actions 端点 404。
- `unauthorized` / `forbidden` / `rate-limited` / `unreachable` / `timeout` / `redirect` / `invalid-response` / `error` 分别返回。
- `instance-missing` / `credential-missing` 表示 Locus 配置前提不满足。

### CLI 与 Workspace

- `gitea instance ...` 管理实例配置，不验证网络。
- `gitea repo inspect/suggest/link/unlink`：查询、候选、显式关联/解除。
- `gitea repos/status/runs/run show`：从已保存关系聚合观察；插件停用仍显示关系。
- `gitea ci`：读取本地 Git HEAD，在 Remote 与关联仓库完整名称一致时按 `head_sha` 查询；无 Run 返回 `empty`，Remote/仓库不一致返回 `unmatched`，不猜测对应关系。

`gitea repo link` 要求 Workspace 已选择 `locus.gitea`；实例与仓库查询不要求 Workspace。一个 Workspace 可关联多个仓库，多个 Workspace 可共享同一引用。CI Run 不自动建立 Machine 或部署关系。

## 测试

### 包内/跨包

- 实例 CRUD、URL 与凭据名称校验、重复名称/地址拒绝、重启恢复。
- DSH credentials 优先，环境回退；401、credential-missing、redirect 不跟随。
- 仓库按 owner/repo 与数字 ID 解析；改名后引用稳定。
- Run 成功/失败/运行中、空列表、Actions 未启用、API 404、限流、时间字段。
- Git Remote HTTP/SSH 候选；请求不自动发生；关系不自动写入。
- CLI 多 Workspace 共享、无本地仓库关联、`gitea ci`、插件停用后关系保留。

### 真实 Gitea 1.25.5

- 版本/用户/认证成功；5 个私有仓库可读。
- `CZXyee/2608-freight-platform`：Run 135 success，`head_sha` 过滤命中 3 条；Run 详情含 `pro-host-probe.yaml@refs/heads/dev` 与起止时间。
- `CZXyee/test`：Run 14 failure，准确返回 `conclusion=failure` 与提交 `a1b390…`。
- 两个 Workspace 共享同一 `instance:repository` 引用；无本地仓库也可直接关联。
- 本地临时 Git HEAD `eef8ca…` 与 Remote 匹配，`gitea ci` 返回 3 条成功 Run；另一本地 HEAD 无 Run 返回 `empty`，非对应仓库返回 `unmatched`。
- 实例地址改为不可达端口后关系保留并报告 `unreachable`；恢复地址后重新可读。
- 凭据缺失与无效 Token 分别报告 `credential-missing` / `unauthorized`，关系保留。
- Plugin 停用后 `gitea repos` 显示 `unavailable`，`workspace show` 保留关系。
- 真实 Gitea 列表端点忽略 `limit`；客户端截断已验证。该事实已写入模块 README。

### 未验证或限制

- 未改名真实仓库；改名稳定性由 fake API 的数字 ID 路径验证，真实实例未执行破坏性改名。
- 未验证 Actions 未启用、API 不支持的线上实例；fake API 覆盖分类。
- 未下载日志/Artifact，未读取 Secret/环境变量，未触发或取消 CI。
- 未建立 CI→Machine→部署/服务健康关系；没有真实部署证据，不自动推断。
- 当前交互环境中未观察到 Gitea 模块 HMR 替换；DSH 重启与长驻 shell 连续命令已验证，不能把 Gitea HMR 写成已验证事实。

## 后果

- 新增 `@locus/gitea`、`locus.gitea` Capability 与 `locusGitea` 服务；Core 只新增来源限定的 Workspace 关系，不新增 Gitea schema。
- Gitea 实例配置独立持久化；Run/Workflow/日志/Artifact 不进入 Locus，外部不可达不删除关系。
- Git Remote 只产生候选，`gitea repo link` 才写关系；CI 成功不建立 Machine 或部署关系。
- 凭据只保存名称并通过 DSH credentials 优先解析；Token 不进入配置、Core、错误或日志。
- 当前只读边界不含触发/取消 CI、日志/Artifact、Secret/变量管理与部署推断；这些需要独立授权、证据和回滚条件。

## 备选方案

**把 Run 历史复制到 Locus。** 会形成第二套 CI 缓存、分页与恢复语义，且很快过期；不采用。

**用 owner/name 作为仓库 ID。** 改名即断引用；不采用。

**把 Token 写进实例配置或用 URL 查询参数。** 容易泄露到日志、备份与错误；不采用。

**把所有 404 当成“没有 Run”。** 会把权限、Actions 未启用、API 不支持误写成空结果；不采用。

**Run 成功即关联部署 Machine。** 缺少真实部署证据，且会把 CI 事实扩成部署事实；不采用。

**建立通用 SCM/CI Provider Framework。** 当前只有 Gitea 一个真实提供方；不采用。

## 后续

- 部署观察与远程执行需要独立的部署证据、目标 Machine、凭据和回滚条件。
- CI→部署闭环可组合 Gitea Run、Connectivity Profile 与 Machine，但关系必须由真实部署事实确认。
- 日志/Artifact、Workflow 触发、Secret 与变量管理涉及敏感读取或写操作，需单独授权与审计。
