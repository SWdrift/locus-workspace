# 决策记录：领域生成、操作契约与应用投影

Status: proposed

## 问题

已交付领域在 CLI 中各自形成命令命名空间，但同名动词的领域含义并不相同：`machine register` 确立长期机器身份且不要求机器在线，`fs register` 只登记一个发现位置而不确认成员，`connect profile add` 保存连接配置但不建立连接，`git confirm` 确认观察到的仓库关联但不取得仓库。命名空间只隔离名称与操作身份，不能提供领域语义。

新增一个领域当前要分别修改共享类型、领域 Plugin、`plugins/cli/src/commands.ts` 中的手写命令、DSH profile 装配和文档；CLI 实际成为领域能力的唯一用户入口与命令结构定义位置。`packages/contracts` 也已随每个领域增长，集中保存各领域服务接口，使同一个包同时承担公共契约与领域契约。另一方面，Core 若开始理解 Git、Session、部署等领域概念，就会演变为通用业务平台或完整 Ontology，违背既有组件边界。

目标是 Domain → Applications 的开放生成机制：新增领域通过定义自身的领域原语、可消费契约和实现，能够在不修改公共机制或其他领域的前提下，被不同应用发现、组合与使用。各应用通过独立投影提供适合自身交互方式的操作与视图，领域语义及其正确性约束不由应用重复定义。CLI 是第一个验证场景，不是设计中心；本文给出该方向的设计、验证标准与风险，机制尚未实现，任何部分都不构成已交付契约。

## 提案

### 领域、应用与投影

```text
Core · 公共契约与机制
    Identity / Relation / Contract / Capability
        ↓
Domains
    Workspace / Machine / Connectivity / Git / Session / Gitea
    领域类型、操作、查询、状态、约束、契约
        ↓
Application Composition（可选、可复用）
    按需组合领域能力，形成应用用例与视图数据
        ↓
Applications（同级消费者）
    CLI   → Commander / shell
    UI    → 页面 / 表单 / 交互
    Agent → MCP / 能力发现
```

Application Composition 不一定是独立模块或强制中间层，各应用也可以直接调用领域能力。MCP、Commander 与 HTTP API 是应用可选择的接口与协议，不是与 CLI、UI、Agent 同层的应用。

应用可以组合领域，但不能拥有被组合领域的语义。`workspace overview` 在 CLI 内组合多个领域公开用例；未来 UI 若需要同一个 Overview，却分别实现领域解释、确认关系与未知状态处理，就会产生重复逻辑。因此，可复用的应用组合能力应能独立于 CLI 与 UI 存在；但在 UI 需求出现前，不预建庞大的 Application Framework。

### 领域契约的暴露范围

领域对外暴露的不应只有 Operation。不同应用需要不同能力，领域契约可按需包含以下内容，但不要求每个领域全部提供：

| 暴露内容 | 用途 | 当前判断 |
| --- | --- | --- |
| Operation | 任务入口、输入输出与行为保证 | 领域操作的基础 |
| Type / Schema | 类型、约束与领域身份 | 需要可执行校验 |
| Query | 对象列表、详情、关联导航与筛选 | 按真实应用需求提供，不强制统一查询模型 |
| State / Observation | 当前状态、来源、时间，以及缺失、失败与未知 | 领域自行表达，不合并为布尔值 |
| Change / Invalidation | 刷新、订阅、失效与重新核验 | 先按真实需求，不预建通用事件系统 |
| View / UI 映射 | 表单、列表、详情与交互呈现 | 应用投影，不属于领域语义 |

这些能力首先作为领域契约的一部分存在，不因出现一次就升级为 Core 原语。Entity、Query、Event、View 不预先规定为所有领域的必备结构；只有当多个应用出现相同需求，并且标准形态能被真实校验时，才考虑公共机制。

### 两类可组合性

| 维度 | 目标 | 判断依据 |
| --- | --- | --- |
| 领域间组合 | 语义相容与行为正确性 | 类型映射、前置条件、适配、核验与外部状态 |
| 领域与应用组合 | 能力可用、交互一致与呈现恰当 | 同一契约可被不同应用消费，Outcome 一致 |

领域间组合回答“A 的保证能否建立 B 的条件”；领域与应用组合回答“同一领域能力如何被 CLI、UI 与 Agent 使用”。二者不能互相替代：应用投影不能重定义领域语义，领域契约也不能规定应用的布局与交互流程。

例如 `connect verify` 在 CLI 中以退出码 2 表示未连接，UI 可以呈现为“无法连接”的状态与诊断详情，Agent 接口返回结构化结果。三者不需要共享表现形式，但必须表达同一个领域 Outcome。

### 操作契约

操作契约把调用形式扩展为可检查、可组合的约定，概念形式为 `C = (I, O, P, Q, E, V)`：

| 要素 | 含义 |
| --- | --- |
| `I` | 输入类型与约束 |
| `O` | 输出类型与约束 |
| `P` | 前置条件 |
| `Q` | 后置条件或行为保证 |
| `E` | 副作用及执行约束 |
| `V` | 结果验证与核验机制 |

这是概念模型，不意味着六个属性立即成为公共 API 的必填字段。

操作组合至少需要输入输出之间存在明确的类型映射，且后续操作的前置条件能够由先前操作的保证、适配过程或运行时检查建立：`Q_A ∧ G ⇒ P_B`。`G` 可以是适配器、附加检查或 Guard；没有 `G` 时，不能仅凭类型把两个操作连接起来。

领域类型身份不能由结构类型代替：`MachineId` 与 `WorkspaceId` 在 TypeScript 中可能都是 `string`，跨进程 JSON Schema 也只能检查字符串结构。跨领域组合必须声明身份映射与校验方式。外部状态还会变化，操作 A 完成时成立的条件不保证操作 B 执行时仍然成立；必要时在 B 执行前重新检查前置条件，无法核验时拒绝执行或保留未知结果。

契约声明不自动证明实现正确，一次验证也不保证未来持续成立。类型相容只解决接口层；目标对象存在、权限与配置满足属于行为条件；外部结果仍需真实观察。

### 应用投影

Operation Contract 足以描述调用、输入验证与基础表单，但不足以唯一生成完整 UI：

| 应用需求 | Operation Contract 是否足够 |
| --- | --- |
| 调用操作、输入验证 | 基本足够 |
| 自动生成操作表单 | 可生成基础表单，需要 UI 映射规则 |
| 对象列表、详情与关联导航 | 需要查询、关系与领域状态语义 |
| 动态状态、刷新与订阅 | 需要观察、失效与更新机制 |
| 多领域信息聚合 | 需要应用级组合逻辑 |
| 布局、交互流程、视觉层次 | 无法由操作契约唯一确定 |

例如 `machine` 领域在 CLI 中投影为 `machine list`、`machine show`、`machine address add` 与 `machine observe`；UI 还需要机器列表、详情、多地址管理、关联 Workspace、SSH 观测状态、最近一次观察时间，以及操作失败后的反馈。它们消费同一领域能力，但不是同一种表现形式。

CLI 投影声明决定命令路径、位置参数、选项、帮助与确认规则；`--yes` 属于具体投影的交互规则，不是所有写操作的统一语义：

```text
Operation: machine.observe
CLI projection:
  path: ["machine", "observe"]
  args: ["machine", "address?"]
  options: []
  confirmation: none
```

UI 投影可以声明字段映射、列表列、操作入口与状态呈现，但其具体格式由真实 UI 需求决定，当前不预先冻结。

应用不必完全由领域自动生成。契约可以生成通用操作入口、基础表单与基础视图，但真正有价值的 Workspace 工作台仍需要应用级的信息组织、交互设计与跨领域组合。投影声明可以与领域契约一起交付，但不得成为领域运行逻辑的必需依赖，也不得为了适配某个应用反向修改领域契约。

### Definition 与 Provider

Operation Definition 负责可发现性与接口结构，Active Provider 负责当前可执行性。两者只有在安装与发现也独立时，才能同时满足“Provider 缺省时入口仍可见”和“新领域不修改应用核心”：

| 状态 | 操作入口表现 |
| --- | --- |
| Definition 已安装，Provider 已加载 | 入口存在，继续检查能力选择、授权与执行条件 |
| Definition 已安装，Provider 未加载 | 入口存在，调用时报告不可用 |
| Definition 未安装 | 入口不存在，不能凭空推断结构 |

CLI 命令树只是操作入口的一种实例。可候选的 Definition 来源包括 DSH profile 中的纯契约模块、构建期清单或包元数据；无论选择哪种，必须满足：不执行领域 Plugin 的初始化逻辑也能获得 Definition，且安装、发现、注册、更新和卸载的状态可观察。现阶段不选定 Manifest 或 Registry 格式，但验收必须证明这一性质。

可发现、已提供、已授权与可执行是不同状态：`Discoverable ≠ Provided ≠ Authorized ≠ Executable`。Operation Catalog 只负责发现与提供方绑定，不代替 Workspace Capability 选择，也不自动授予调用权限。`fs inspect` 是否可执行还取决于能力选择、位置登记与原生权限；连接配置、凭据与外部可达性同理。

一次调用应使用稳定的 Definition 与兼容的 Provider 绑定。只保留 Definition 快照并不充分：若 Definition v1 已解析输入，而 Provider 在分派前更新为语义不同的 v2，实际契约仍然不匹配。调用期间发生替换时，保留可安全继续的旧绑定，或中止并报告结果未知；不能无条件切换到新版本，也不能把中断写成成功。

### 生成层次

| 层次 | 内容 | 当前判断 |
| --- | --- | --- |
| L1 契约与首个投影生成 | 将已实现领域的操作整理为契约，生成 CLI 命令树、参数校验、帮助与基础入口 | 工程可行性较明确；CLI 只验证一种投影 |
| L2 能力与应用组合 | 领域间组合，以及可复用的应用用例与视图数据 | 需要适配、协调与核验；以 `workspace overview` 为对照 |
| L3 原生领域生成 | 由 Agent 创建新的领域类型、状态、不变量、持久化和操作实现 | 长期目标；Schema 与测试数量不能保证语义正确 |

`workspace overview` 已经手写组合 Workspace、Filesystem、Git、Session、Machine、Connectivity 与 Gitea，并区分确认关系、本次观察、未确认建议与未知项。L2 若只是把它改名重写，不构成契约驱动的组合生成；实验必须产生一个具有独立检查与核验条件的新操作，或把 overview 的领域解释提取为可被多个应用复用的组合，并与现有实现比较维护成本与重复声明数量。

CLI 是第一个证明机制有效的应用；UI 或另一个独立消费端可能反过来暴露 CLI 没有覆盖的契约需求。两者共同推动公共机制演化，而不是让某一个应用的形式决定领域应该长什么样。

### 兼容性不变量

- 保留 DSH profile 启动与 `appReady` 生命周期。
- 保留可选领域服务的缺失语义：入口可发现，调用明确失败，长期关系与配置保留。
- 保留长驻 shell 逐行解析、每行重建命令树与开发期 HMR。
- 保留 `--json` 输出纯净性与 stderr 诊断；人类与 JSON 输出表达同一领域 Outcome。
- 保留成功 0、参数错误 1、业务或依赖失败 2 的退出码规则。
- 保留显式 `--yes` 的破坏性操作约束。
- 保留当前命令名称、参数与领域 Outcome 语义；投影不重新解释业务结果。
- Definition 与 Provider 的绑定必须版本兼容；调用期间发生替换时保留安全绑定或报告未知，不静默切换语义。
- 应用组合逻辑不依赖 CLI 的命令结构；CLI、UI 与 Agent 消费同一领域 Outcome。
- 领域业务用例不依赖 CLI，后续 Web 调用同一用例而不解析 CLI 文本。

### 与 Connector 的关系

| 概念 | 含义 |
| --- | --- |
| Connector | 对外部服务 API、认证、事件与调用的集成实现 |
| Connection | 某个具体服务实例或账户的可用连接配置 |
| Link | Locus 自己保存的跨对象持久关联 |
| Domain | 拥有局部类型、行为、约束和可能的持久状态的语义领域 |

Connector 扩展 Locus 能接触的现实系统，领域生成扩展 Locus 能理解和执行的工作能力。Connector 可以作为领域生成的材料，但并非每个 Connector 都需要转化为独立领域；接入 Gitea 不等于自动获得 CI/CD 或部署领域。

### 工程路线

1. 领域契约所有权试验：为 Remote Machine 增加纯契约导出（类型、Schema 与 `machine.observe` 定义），由 Host 在未初始化 Plugin 的路径上读取；验证新增领域不修改公共 `packages/contracts`。既有领域暂不强制迁移。
2. Definition 安装与发现：明确来源、安装、更新与卸载状态，验证“已安装未加载”“未安装”与“已加载”三态。此步不生成 CLI。
3. 已有操作契约化：选择 `machine observe` 与 `connect verify`，整理为可供程序消费的契约，保留原有领域实现。
4. 首个应用投影：根据契约与 CLI 投影声明生成 Commander 命令树，与现有命令的名称、参数、帮助、输出和退出码对照。该步只验证一种投影。
5. 生命周期与可执行性：验证插件缺省、运行时替换、shell 热更新、能力选择、授权与调用中的版本绑定同时成立。
6. 应用组合试验：把 `workspace overview` 的领域解释提取为可复用组合，或生成一个与 overview 不同、带独立检查与核验条件的组合操作；比较重复声明、公共代码修改量与维护成本。
7. 第二消费端试验：用最小 UI 或其他非 CLI 消费端读取同一契约，验证它不依赖 CLI、能表达相同 Outcome，并暴露 CLI 未覆盖的查询、状态或视图需求。
8. Agent 生成试点领域：按约定生成契约、TypeScript 实现、测试和文档；允许修改 DSH profile 与安装清单，检查不修改 Core、应用核心或其他领域即可获得新能力。

## 备选方案

**以 CLI Generator 为中心。** 命令树最容易生成，也能快速看到效果，但会把契约设计拉向命令语法；UI 与 Agent 随后会暴露列表、状态、刷新与布局需求，迫使契约反复返工。CLI 作为第一个投影，机制以 Domain → Applications 为目标。

**把所有接口协议当作同级应用。** Commander、MCP 与 HTTP API 是应用可选择的呈现与通信方式，不拥有独立的领域解释或应用组合。把它们与应用并列会模糊“谁消费能力、谁定义协议”。

**所有领域统一提供 Entity、Query、Event 与 View。** 统一模型能让生成器看起来完整，但会让没有这些需求的领域填充占位结构，并把 UI 概念写入 Core。只暴露真实应用需要的能力，标准形态由重复需求推动。

**在 UI 开发前先建 Application Framework。** 没有第二个消费端时，框架只能按 CLI 的形态推断复用边界，容易变成新的中间层。先允许应用直接调用领域能力，在 overview 出现第二个消费者时提取组合。

**要求应用完全由契约生成。** 契约可以生成操作入口、基础表单与基础视图，但 Workspace 工作台需要信息组织、交互设计与跨领域组合。完全生成会把应用设计伪装成 Schema 推导。

**公共 Contracts 继续集中全部领域接口。** 类型引用简单，但每新增领域都要修改公共包，公共包无法独立于领域集合演进，也无法证明领域所有权。改为领域自带纯契约导出，公共包只保留跨领域机制。

**统一公共动词或通用 CRUD 框架。** 各领域都会出现 `create`、`register`、`inspect`、`remove`，看起来可以共享一套动词和处理器。但同名操作的前置条件、副作用与结果保证不同，统一模型会迫使 Core 解释领域语义，或让差异藏在参数里。只共享命名空间，不共享业务动词。

**Core 吸收领域知识或建立完整 Ontology。** 集中定义 Machine、Repository、Session、Deployment 能让组合看似直接，但 Core 会持续膨胀为企业平台，Plugin 自治与独立持久化随之失效。公共契约保持最小必要性，领域知识留在 Plugin。

**无契约的任意代码调用或自动组合。** 只按 TypeScript 结构把输出接到输入，无法表达 `Q_A ∧ G ⇒ P_B`、授权、效果与核验，容易产生不可验证的组合。类型信息继续保留，但组合必须同时检查行为条件与外部事实。

**先建立 Manifest 与中央 Registry。** 看似一次性解决发现与安装，但会把版本、刷新、权限和多 Host 一致性问题提前集中，并可能形成新的集中式注册清单。先验证最小发现路径，再决定是否引入清单或目录服务。

**静态生成 Commander 源码。** 生成一次源码可以在构建期检查，但与领域插件缺省、运行时替换和 shell 热更新冲突，还会让 CLI 结构成为第二个需要同步的产物。采用运行时根据 Definition 构造命令对象。

**新建独立 Host、通用 RPC 或中央插件总线。** 现有组件边界已明确 DSH/Cordis 是唯一宿主，`host-dsh` 保持薄装配，没有第二宿主调用方。领域生成复用现有装配与生命周期，不预建可替换 Host。

**由 Agent 任意生成并装载模块。** 这样生成自由度最大，但会绕过权限、持久化与系统不变量。生成领域进入操作面必须满足契约、能力依赖、授权、生命周期和验证要求；接受契约不等于接受任意内部行为。

**引入完整形式化验证器或重新设计 TypeScript 类型系统。** Design by Contract、Assume–Guarantee 与 Effect Systems 提供了推理基础，但当前收益与成本未经验证。先使用可执行 Schema、运行时约束和真实核验，不把研究性机制设为交付前提。

## 验收标准

每步以其可观察结果判定完成，不以代码或类型存在代替运行证据：

1. 领域契约所有权：试点领域只新增自身契约导出；公共 `packages/contracts` 没有新增领域类型，依赖方向检查通过；既有领域未迁移不阻断实验。
2. Definition 发现：不执行 Provider 初始化即可列出 Definition；已安装已加载、已安装未加载、未安装三种状态可观察；未安装的领域不出现在入口中。
3. 操作契约：`machine observe` 与 `connect verify` 的契约可被程序读取，输入输出、前置条件、效果、核验与领域身份明确，现有领域行为不变。
4. CLI 投影：生成命令在命令名、嵌套路径、位置参数、选项、帮助、人类输出、`--json` 结构与退出码上与现有实现一致；投影声明能表达 `--yes` 等交互规则；领域实现不变。此项只证明一种投影。
5. 生命周期与可执行性：Plugin 缺省时入口仍可发现并明确失败；插件替换或 shell 热更新后使用当前 Provider；调用中发生替换时保留安全绑定或报告未知；能力未选择、未授权与 Provider 缺失分别表达；Catalog 不授予权限。
6. 应用组合：以 `workspace overview` 为基准，提取或生成的组合具有独立的检查与核验条件，不是改名后的聚合函数；组合逻辑不依赖 CLI，不新增中央 Registry、通用查询引擎或领域持久化；重复声明与维护成本可以比较。
7. 第二消费端：同一领域契约可被 CLI 与至少一个非 CLI 消费端（最小 UI 或独立测试消费端）读取；后者不导入 CLI，能表达相同领域 Outcome，并以不同形式呈现；不重复领域语义与未知状态处理。
8. Agent 试点：生成的新领域具有契约、实现、测试与文档，不修改 Core、应用核心或其他领域即可获得能力；允许修改 DSH profile 与安装清单。免手工装配或自动发现安装作为独立验收项，不计入本项。

整体成功标准还包括：新增领域需要修改的公共代码量下降；领域间重复声明减少；每个领域仍需手写的专用 CLI 适配逻辑减少；应用组合不因 CLI 与 UI 分别实现而重复；领域契约不依赖任一应用的命令结构或页面结构。

## 风险

**CLI 中心化设计。** 契约字段、错误表达和默认值容易围绕命令树形成，UI 与 Agent 随后只能适配。需要第二消费端尽早验证契约的可消费性。

**应用组合重复。** `workspace overview` 的领域解释、确认关系与未知状态处理可能被 CLI、UI 与 Agent 各写一遍。可复用组合必须独立于具体应用，但也不能在没有第二个消费者时过早抽象。

**契约范围膨胀。** Query、State、Change、View 一旦被设为所有领域的必备结构，领域会被迫填充占位实现，公共机制重新长出应用框架。只按真实需求暴露，标准形态由重复需求推动。

**生成应用被误认为完整工作台。** 基础表单与视图可以由契约生成，但信息组织、交互流程与跨领域组合仍需应用设计。把生成结果当作完整应用会掩盖真实工作缺口。

**领域契约迁移风险。** 把领域契约移出公共包可能引入循环依赖、重复类型、构建顺序与发布边界问题。迁移必须按领域增量进行，公共包在过渡期保留必要兼容入口，不能为了一次性拆分制造新的抽象层。

**领域类型身份不明确。** 结构相同或底层都是 `string` 的标识符容易被误当作可互换；跨进程 Schema 与 TypeScript 结构类型都不能自动证明领域身份。组合与投影必须显式声明身份映射与校验。

**公共原语扩张。** 一旦 Operation、Type、Effect、Outcome、Evidence、Query、View 都被设为必填，公共层会重新长出领域与应用语义。最小必要性只能由真实领域和应用检验。

**Definition 来源集中化。** 构建期清单或宿主 Registry 可能成为新的集中式注册表，重新要求每个领域修改中央文件。发现机制必须允许领域独立安装，且不执行 Provider 初始化。

**把声明当作保证。** Schema、契约文本与测试数量容易让读者误以为实现已满足业务条件，或让一次成功观察被当成持续事实。文档与投影必须分别表达领域 Outcome、调用错误和未观察状态。

**投影元数据扩张。** 命令路径、参数、选项、确认、字段映射、列表列与状态呈现可能演化为第二套领域模型，或反向要求领域契约适配某个应用。投影声明必须保持在接口层，领域运行时不依赖它。

**投影与领域语义偏离。** `fs inspect` 返回 missing、`git inspect` 返回 not-repository 仍可能是成功查询，而 `connect verify` 未连接当前以退出码 2 表达。生成器或应用若自行推断成功或失败，会破坏既有语义。

**生命周期与缓存一致性。** Definition 从安装包、契约模块还是活动插件发现，决定了多 Host、热更新与接口缓存是否一致；Operation Catalog 的轻量实现也可能在插件替换时返回过期定义或绑定不兼容的 Provider。

**第二消费端缺位。** 若只有 CLI 使用契约，所谓“应用无关”无法验证，契约会逐渐退化为命令模型。第二消费端必须进入验收，而不是停留在未来计划。

**治理缺位。** 若 Agent 生成的领域可以自我声明、自我批准并直接生效，契约就退化为自我认证。评价、批准、启用、隔离与停用需要真实调用方与权限边界，不能由生成器自行决定。

**抽象成本高于收益。** 契约、注册、投影生成器、应用组合与验证机制本身需要维护；如果真实新增领域很少，或差异远大于共性，这套机制的成本可能高于它消除的重复装配。路线以真实收益决定是否继续。
